# UI/UXデザイン — 制作指示書

DB: `db/references/`（10,000件 / ID `UI-xxxxx`）。アプリ種別（16）× プラットフォーム（7）× UXパターン × UX法則 × スタイル。
各レシピにペルソナ・画面一覧・使うコンポーネント・デザイントークン・成果物リストが入っています。

```bash
node tools/search.mjs --genre uiux 家計簿 iOS
node tools/search.mjs --genre uiux ダッシュボード CRM --style グラス
```

## テンプレート

| テンプレート | 内容 |
|---|---|
| `app-prototype` | スマホアプリのクリック可能プロトタイプ（PCではiPhoneフレーム表示）。オンボーディング(スワイプ)→ホーム(スケルトン・楽観的UI・トースト取り消し)→詳細(ヒートマップ・棒グラフ)→ボトムシート(入力検証)→完了(線描画チェック＋紙吹雪＋level-up音)。ダークモード対応 |
| `dashboard` | SaaS管理画面。KPIカウントアップ＋スパークライン / ホバーでツールチップの折れ線グラフ / ドーナツ / ソート・絞り込みテーブル / ⌘Kコマンドパレット / トースト / 折りたたみサイドバー / ダークモード / SP時はボトムナビ |

## UI/UX案件の進め方（成果物の順番）

1. **リサーチ・定義**：ペルソナ（DBの `persona`）、課題、主要タスクを1文で定義
2. **フロー**：画面遷移図（DBの `screens` を矢印でつなぐ）。主要タスクは3タップ以内
3. **ワイヤーフレーム**：グレーだけで情報の優先順位を決める
4. **デザインシステム**：`tokens.css`（色）＋ DBの `design_tokens`（角丸・余白・影）＋ コンポーネント一覧（`components`）
5. **ハイファイ＆プロトタイプ**：テンプレートを改造して「触れる」状態で納品 → クライアント・ユーザーテストで検証
6. **インタラクション仕様書**：DBの `ux_patterns`（動き・音）とタイミング（下表）を表にして渡す

| 用途 | 時間 | イージング |
|---|---|---|
| ホバー・押下 | 100ms | ease-out |
| トグル・チェック | 200ms | spring `cubic-bezier(.34,1.56,.64,1)` |
| モーダル・シート | 300ms | ease-out（出現）/ ease-in（退場） |
| 画面遷移 | 400〜500ms | ease-in-out |

## プロの基準

- **全ての状態をデザインする**：通常 / ホバー / 押下 / フォーカス / 無効 / 読込中（スケルトン）/ エラー / 空状態 / 成功
- **UX法則で説明できるデザイン**（DBの `ux_laws`）。提案時に「なぜこの配置か」を法則で説明すると説得力が出る
- タップ領域44px以上、重要操作は親指の届く画面下部（フィッツの法則）
- エラーメッセージは「何が起きたか＋どうすればいいか」（例：メールアドレスの形式が正しくありません（例：name@example.com））
- 効果音は **フィードバック** として使う：成功 `success` / 追加 `pop` / エラー `error` / 通知 `notify` / スワイプ `swipe`。必ずOFFにできること
- 触覚フィードバック：`navigator.vibrate(10)`（Android）
- ダークモードは「黒反転」ではなく、面の階層（bg < card < 浮いた要素）で明度を上げる

## Figma で納品する場合

HTMLプロトタイプで仕様を固めてから、スクリーンショット（`render.mjs`）を Figma に貼り、
トークンを Figma Variables に登録して清書する（色名は `--c-*` と同じ名前に揃える）。
